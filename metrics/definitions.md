## 0. 원칙

1. **정의는 결과를 보기 전에 고정합니다.** 결과를 본 뒤 정의를 바꾸면 특정 알고리즘에 유리하게 바꿨다는 의심을 피할 수 없습니다.
2. 정의를 바꿔야 하면 9절 변경 기록에 이유를 적고, **모든 알고리즘·모든 에피소드에 다시 적용**합니다.
3. 모든 지표는 **에피소드 하나 × 알고리즘 하나** 단위로 계산합니다.
4. 모든 지표는 **낮을수록 좋습니다.** 높을수록 좋은 값(성공률)은 1에서 뺀 값(실패율)으로 저장합니다.
5. **실패를 지우지 않습니다.** 실패 프레임, 키포인트 누락 프레임도 그대로 포함해 계산합니다.
6. 같은 에피소드는 모든 알고리즘에서 같은 프레임 구간을 씁니다. 에피소드를 빼는 기준(8절)도 모든 알고리즘에 똑같이 적용합니다.
7. **알고리즘이 스스로 줄이도록 만들어진 값의 크기는 순위에 쓰지 않습니다** (학생 안내서 5-3). 대신 **모든 알고리즘에 같은 기준으로 우리가 직접 판정한 값**(예: 2.1 성공률)을 씁니다. 알고리즘이 스스로 보고한 성공·실패(status)는 기준이 알고리즘마다 달라 쓰지 않습니다.
8. 지표는 **세 축**으로 봅니다.
   - **정확도:** 리타게팅이 얼마나 잘 되나
   - **속도:** 얼마나 빨리 푸나 (정확도·궤적 품질과 섞지 않고 따로 보는 축)
   - **궤적 품질:** 결과를 실제 로봇에 쓸 수 있나
   - 축마다 **순위** 지표와 **참고** 지표가 있고, 모든 알고리즘에서 0이어야 하는 **안전 확인**이 따로 있습니다.

## 2. 지표

### 정확도 — 리타게팅이 얼마나 잘 되나

#### 2.1 리타게팅 성공률 (`retarget_fail_rate` = 1 − 성공률) — 순위

- **계산:** 출력 관절 각도를 5-1 재생 함수로 돌려 얻은 TCP 자세를 목표 TCP 자세와 비교해, **세 조건을 모두 만족한 프레임**을 성공으로 셉니다.
  ```
  pos_err[t] = ‖ tcp_pos[t] − target_pos[t] ‖
  rot_err[t] = 2·acos( |⟨tcp_quat[t], target_quat[t]⟩| )          (q와 −q는 같은 방향)
  success[t] = pos_err[t] ≤ 0.5 cm  and  rot_err[t] ≤ 1°  and  모든 관절이 한계 안 (ε = 1e-6 rad)
  retarget_fail_rate = 1 − mean_t success[t]
  ```
- **단위:** 비율. 표에는 성공률(= 1 − 값)로도 적습니다.
- **기준값(0.5 cm, 1°)은 결과를 보기 전에 고정합니다 (v1.1, 11/6 변경).** 처음엔 1 cm·5°였으나 "IK가 목표를 얼마나 정확히 푸는가"를 가리려면 더 엄격하게 하자는 결정으로 바꿨습니다. 이 기준은 **IK 풀이 정확도**를 보는 것이고, 목표 자체(사람 키포인트 3D 오차·싱크 오차, 손목 약 7 mm)의 오차는 포함하지 않습니다. 목표가 이미 mm 수준으로 흔들리므로 절대 성공률은 낮게 나올 수 있고, 알고리즘 간 비교가 목적입니다.
- **가이드의 IK 실패율을 대신하는 이유 (v0.4):** IK 실패율은 각 알고리즘이 스스로 보고한 status를 셉니다. 반복 계산하는 알고리즘(A·B)은 수렴 기준을 각자 정하므로, 같은 결과도 기준에 따라 성공이 되기도 실패가 되기도 합니다 (4번 시험: B 95% 오차 2 mm인데 미수렴 80%). 성공률은 **모든 알고리즘의 출력을 같은 목표·같은 기준으로** 우리가 직접 판정합니다.
- 원칙 7과의 관계: 오차의 **크기**를 순위에 쓰는 게 아니라 "쓸 만한 결과를 냈나"를 공통 기준으로 판정하는 것이라, 가이드가 IK 실패율을 순위에 쓰는 것과 같은 성격입니다.
- A가 한계에서 잘라낸 프레임, B가 한계 제약에 막힌 프레임은 손목이 목표에서 벗어나 여기서 실패로 잡힙니다.
- **목표가 NaN인 프레임(손목 미검출)은 판정할 수 없어 분모에서 뺍니다.** 모든 알고리즘에서 같은 프레임이라 비교에는 영향이 없고, 데이터 문제(키포인트 누락)가 리타게팅 실패로 섞이지 않게 합니다. 뺀 비율은 `episode_info.csv`의 `target_missing_rate`에 그대로 기록합니다 (원칙 5). 목표가 전부 NaN이면 NaN입니다. 저크·속도·충돌은 관절 각도가 있으므로 모든 프레임으로 계산합니다.

#### 2.2 팔 회전각 차이 (`arm_angle_diff_rad`) — 참고 (C만 사람 SEW 입력, 11/6 "기존 알고리즘 그대로")

- **무엇:** 7자유도 팔은 손목 자세를 정해도 팔꿈치가 어깨–손목 축 둘레로 돌 수 있습니다. 그 각도(팔 회전각, SEW 각)가 사람과 로봇에서 얼마나 다른지 잽니다. "로봇 팔이 사람처럼 움직였나"를 봅니다.
- **계산:** 사람 어깨·팔꿈치·손목(`kp`)을 `to_robot_point`로 로봇 좌표로 옮기고, 로봇 어깨·팔꿈치·손목(관절 2·4·6 중심)과 **같은 방식**으로 각을 구합니다.
  ```
  a = (W − S) / |W − S|                       어깨→손목 축
  e = 팔꿈치 (E − S)를 a에 수직인 평면에 투영
  r = 아래 방향 (0, 0, −1)을 a에 수직인 평면에 투영
  ψ = atan2( a · (r × e),  r · e )             팔 회전각 (rad)
  arm_angle_diff_rad = median_t | wrap(ψ_로봇[t] − ψ_사람[t]) |      wrap: −π~π
  ```
- **단위:** rad (표에는 °로도 적음)
- 사람 키포인트가 NaN이거나, 어깨–손목 축이 거의 수직(|a·아래| > 0.99)인 프레임은 뺍니다. 쓴 프레임 비율을 `episode_info.csv`에 적습니다.
- `to_robot_point`는 평행 이동·축척·회전이라 각도를 바꾸지 않습니다.
- **참고로 두는 이유 (2026-11-06 갱신):** 세 알고리즘을 기존 방식 그대로 쓰기로 해서 (팀 결정 11/6, T10 대체), A·B는 손목 목표만 받고 C만 사람 SEW 각을 입력으로 받습니다. 그러면 이 값은 C만 스스로 줄이려는 "자기 목표"가 되어, 순위에 쓰면 C에 유리합니다 (원칙 7). 그래서 순위에는 쓰지 않고, "팔꿈치를 사람과 얼마나 비슷하게 두었나"를 알고리즘 특성으로 보고하고 2.1 성공률·2.6 환경 충돌률이 왜 그렇게 나왔는지 설명하는 데 씁니다.
- (이전 2026-11-05: 팀이 A·B·C 모두에 사람 팔꿈치를 입력으로 주기로 했었음, T10. 판정은 그때도 참고)
- 손목만 주는 쪽으로 바뀌면 순위로 올립니다 (그때는 팔꿈치가 각 알고리즘이 정한 결과라서).
- **사람 팔꿈치가 안 보인 프레임 (4번 T4 답, 11/5):** 세 알고리즘 모두 "직전 팔꿈치를 유지"하는 같은 원칙입니다. 보간으로 없는 팔꿈치를 만들지 않습니다.
  - A: 팔꿈치 보조 목표 없이 직전 자세에서 이어 감 / B: 직전 프레임 로봇 팔꿈치 방향을 유지하는 점을 팔꿈치 목표로 / C: EAIK 해 중 직전 자세와 가장 가까운 해
  - 4번 npz `elbow_used`로 사람 팔꿈치를 쓴 프레임이 표시되고, 그 비율을 `episode_info.csv`의 `elbow_used_rate`에 적습니다. 팔 회전각 차이는 사람 팔꿈치가 보인 프레임에서만 계산되므로(사람 키포인트 NaN 프레임 제외) 이 구분과 맞습니다.

### 속도 — 얼마나 빨리 푸나

#### 2.3 프레임당 계산 시간 (`compute_ms_median`, `compute_ms_p95`) — 순위 (속도 축) / 보조 `over_budget_rate`

- **계산:** 4번 `time_ms`에서 **NaN(목표가 없어 풀지 않은 프레임)과 남은 첫 프레임(준비 시간)을 뺀** 값의 중앙값과 95% 값
  ```
  t = time_ms[ time_ms가 NaN이 아닌 프레임 ][1:]
  compute_ms_median = median(t),   compute_ms_p95 = percentile(t, 95)
  over_budget_rate  = mean( t > 33.3 ms )       30 Hz 한 프레임 안에 못 푼 비율 (실시간 초과율)
  ```
- **단위:** ms, 비율. 표에는 실시간 가능 비율(= 1 − 초과율)로도 적습니다. NaN 프레임 비율은 `episode_info.csv`의 `time_missing_rate`에 적습니다.
- **실시간 기준을 30 Hz(33.3 ms) 하나로 두는 이유:** 4번은 `1000 / exo_fps`(59.97 fps면 16.7 ms)를 제안했지만, 본 촬영 exo_front가 T1·T3 59.97 fps, T2 30.00 fps라 그렇게 하면 태스크마다 기준이 달라집니다. 저크·속도(2.4·2.5)도 30 Hz로 맞췄으므로 같은 기준을 씁니다. 지금까지 4번 측정(A 0.3~4.5 ms, B 약 30 ms, C 수십 ms)으로 보면 A만 확실히 기준 안쪽이고, 이 차이 자체가 비교 결과입니다.
- **측정 조건 (4번 T11 답, 11/5):** 같은 노드 고정(`sbatch -w`), CPU 1개(`-c 1`), 단일 스레드(`OMP_NUM_THREADS=1` 등), **프레임당 IK 시간만** (모델 로드·파일 읽기·쓰기 제외). 4번이 노드 이름·설정을 `config.json`에 적습니다. 95% 값과 실시간 초과율을 내려면 npz에 **프레임별 `time_ms`**가 있어야 합니다.
- **해석 시 주의:** 계산 시간은 알고리즘뿐 아니라 **구현 언어·라이브러리**에도 좌우됩니다 (예: EAIK는 C++ 기반, mink는 파이썬 QP). 결과 해석에 이 점을 같이 적습니다.
- 대표 알고리즘 선택은 오프라인 데이터 생성용이라, 속도 축은 정확도·궤적 품질과 섞지 않고 따로 봅니다. 논문 결론과 "케이스별 알고리즘 선택 지침"에 씁니다.

### 궤적 품질 — 결과를 실제 로봇에 쓸 수 있나

#### 2.4 저크 RMS (`jerk_rms`) — 순위

- **계산:** **30 Hz로 맞춘 궤적**에서 관절 각도의 3차 차분 ÷ Δt³의 제곱평균제곱근. 7개 관절과 모든 프레임을 한꺼번에 평균합니다.
  ```
  # 30 Hz로 맞추기 (보간·스무딩 없이 프레임만 고름)
  k  = round( (1/30) / median(diff(ts)) )        # 60 fps 에피소드 → 2, 30 fps 에피소드 → 1
  q  = q[::k],  ts = ts[::k]
  Δt = median(diff(ts))                          # 실제 간격 (≈ 1/30 s)
  jerk[t,j] = ( q[t+3,j] − 3·q[t+2,j] + 3·q[t+1,j] − q[t,j] ) / Δt³
  jerk_rms  = sqrt( mean_{t,j} jerk[t,j]² )
  ```
- **단위:** rad/s³
- **30 Hz로 맞추는 이유:** exo_front가 본 촬영에서 **T1·T3 59.97 fps, T2 30.00 fps**입니다. 저크는 Δt³로 나누므로 fps에 크게 좌우됩니다 (같은 노이즈가 60 fps에서 약 8배). 고르는 것은 저크·속도(2.5) 계산에만 쓰고, 다른 지표는 모든 프레임으로 계산합니다.
- **한계:** 60 fps 에피소드에서 버려진 프레임에만 생긴 짧은 튐은 안 잡힙니다.
- `Δt`가 1/30 s와 0.1% 넘게 다른 에피소드는 `summary.md`에 표시합니다. 실패 프레임도 포함합니다.

#### 2.5 관절 속도 한계 초과율 (`velocity_limit_exceed_rate`) — 순위

- **계산:** 2.4와 같이 30 Hz로 맞춘 궤적에서, 이웃 프레임 사이 각속도가 한 관절이라도 속도 한계를 넘은 구간의 비율
  ```
  v[t,j] = | q[t+1,j] − q[t,j] | / Δt
  velocity_limit_exceed_rate = mean_t any_j ( v[t,j] > vmax[j] )
  ```
- **단위:** 비율
- **왜:** 실제 로봇이 그 속도로 따라갈 수 있는지 직접 봅니다. 해가 바뀌며 생기는 **몇 번의 점프**(예: 닫힌 해 C의 해 전환)는 저크 RMS 평균에 묻힐 수 있지만 여기서는 한 번만 넘어도 셉니다.
- **해석 시 주의:** 사람 시연 자체가 빠르면(케이스 "빠른 동작") 모든 알고리즘이 넘을 수 있습니다. 같은 에피소드 안에서 알고리즘끼리 비교합니다.

#### 2.6 환경 충돌률 (`env_collision_rate`) — 순위 / 세부 `env_obstacle_rate`, `env_elbow_below_table_rate`

- **계산:** 아래 둘 중 하나라도 해당하는 프레임의 비율
  ```
  ① obstacle[t] = 로봇 링크가 장애물 상자를 파고듦 (접촉 거리 < 0)
  ② below[t]    = 로봇 팔꿈치(관절 4 중심)가 테이블 위 영역에서 테이블 면보다 아래
                  (테이블 좌표로 되돌린 팔꿈치 p:  p.z < 0  and  (p.x, p.y)가 테이블 윤곽 다각형 안)
  env_collision_rate = mean_t ( obstacle[t] or below[t] )
  ```
  ①, ② 각각의 비율도 세부로 기록합니다.
- **단위:** 비율
- **① 장애물:** 3번 `obstacles.json`의 상자를 `to_robot_point`로 옮겨(꼭짓점 8개를 옮겨 상자를 다시 세움, `replay/scene.md`) 재생 장면에 넣습니다. 장애물이 없는 에피소드는 ① = 0.
- **② 팔꿈치–테이블:** 사람 팔꿈치는 테이블 위에 있는데 로봇 팔꿈치가 테이블 아래로 들어갔다면 알고리즘이 고른 팔꿈치 자세가 잘못된 것입니다. 테이블을 상자로 넣지 않고 **면 + 윤곽**으로 판정해서 `link1`·`base`가 면에 걸리는 문제가 없습니다.
  - **테이블 위 영역에서만** 셉니다. 테이블 옆에서는 팔꿈치가 테이블 높이보다 낮아도 정상입니다(팔을 내린 자세).
  - 테이블이 **앞뒤가 평평하고 양끝이 둥근 좌식 테이블**(약 0.8 × 0.6 m)이라, 테이블 위 영역을 **태스크별 윗면 윤곽 다각형**으로 정합니다 (`metrics/table_outline.json`). 가장자리 y값 하나로 자르면 테이블 옆 바깥까지 테이블 위로 세게 됩니다.
  - 윤곽은 exo_front 프레임에서 테이블 가장자리 점을 찾아 테이블 면(z = 0)으로 옮기고, 이상한 점을 뺀 뒤 볼록 껍질로 만듭니다 (`metrics/table_outline.py`, 방법·결과 `metrics/table_outline.md`). 세 태스크 크기가 0.79~0.82 × 0.61~0.62 m로 같은 테이블이고, 가장자리는 1~2 cm 안팎의 오차가 있을 수 있습니다.
  - 로봇 팔꿈치를 `to_robot_point`의 역변환으로 테이블 좌표로 되돌려 판정합니다.
- **순위로 둔 이유 (v0.4):** ②는 사람이 보여 준 팔 자세에서 벗어난 알고리즘의 팔꿈치 선택을 직접 잡아냅니다 (팔꿈치 처리 차이가 드러남). v0.3까지는 "알고리즘이 장애물을 모른다"는 이유로 참고였지만, 테이블 면 판정은 그 이유에 해당하지 않아 순위로 올렸습니다.
- 장애물·테이블 정보가 없으면 0이 아니라 NaN입니다.

#### 2.7 자기 충돌률 (`self_collision_rate`) — 순위

- **계산:** 로봇 몸체끼리의 접촉 중 거리가 음수(파고듦)인 쌍이 하나라도 있는 프레임 수 ÷ 전체 프레임 수
- **단위:** 비율
- **검출 조건:** 제외 쌍 **2개: `base`–`link1`, `link5`–`link7`** (`replay/collision_exclude.md` 확정, 멘토 Q4).
- **해석 시 주의:** 충돌 형상이 구(sphere) 여러 개로 근사돼 있습니다. 모든 알고리즘에 같은 조건이라 비교는 유효합니다.
- 모두 0이면 순위에 영향이 없고, 0이 아니면 알고리즘이 손목을 베이스 쪽으로 접는 등 실제 차이를 보여 줍니다.

### 안전 확인 — 모든 알고리즘에서 0이어야 함

#### 2.8 관절 한계 위반율 (`limit_violation_rate`)

- **계산:** 어느 한 관절이라도 한계를 `ε = 1e-6 rad` 넘게 벗어난 프레임 비율
- **안전 확인인 이유:** A는 잘라내고, B는 제약으로 풀고, C는 한계 밖 해를 버려서 셋 다 구조상 0입니다. 0이 아니면 구현이나 관절 순서 오류를 먼저 확인합니다. 한계 밖 프레임은 2.1에서도 실패로 셉니다.

### 참고 — 순위에 안 씀, 원인 분석·논문 설명용

#### 2.9 추종 오차 (`track_pos_err_mean_m`, `track_pos_err_max_m`, `track_rot_err_mean_rad`, `track_rot_err_max_rad`)

- **계산:** 2.1의 `pos_err`, `rot_err`(재생으로 직접 계산)의 평균과 최댓값. 목표가 NaN인 프레임은 뺍니다. 목표가 npz에 없으면 4번 `pos_err`, `rot_err`를 대신 씁니다 (`episode_info.csv`의 `error_source`에 적음).
- **왜 참고:** 각 알고리즘이 스스로 줄이는 값의 크기라 순위에 쓰지 않습니다 (원칙 7). 2.1 성공률이 왜 그렇게 나왔는지 설명합니다.

#### 2.10 관절 한계 근접률 (`limit_proximity_rate`)

- **계산:** 어느 한 관절이라도 한계에서 δ = 1° 안에 있는(넘은 것 포함) 프레임 비율
- **v0.4에서 순위 → 참고:** 한계에 막혀 목표를 못 따라간 경우는 2.1 성공률이 잡습니다. 남는 것은 "목표는 맞췄지만 한계에 붙어 버틴 경우"(4번 시험: B 2번 관절 81% 한계)인데, 사람 동작이 그 자세를 요구할 때 충실히 따라간 것까지 벌점이 되고 δ도 임의적이라 순위에서 뺐습니다. 실제 로봇에서 여유가 없다는 설명에 씁니다.

#### 2.11 파지점 거리 (`grasp_dist_m`)

- **계산:** 파지 프레임 `g`에서 로봇 TCP와 사람 파지점(엄지 끝·검지 끝 중점, exo 3대 삼각측량, `to_robot_point`로 옮김) 사이 거리
  ```
  grasp_dist_m = ‖ tcp_pos[g] − to_robot_point( (kp[g, thumb_tip] + kp[g, index_tip]) / 2 ) ‖
  ```
- **단위:** m. **첫 파지만** (`grasp_frame` 하나, 멘토 Q3). `kp[g]`가 NaN이면 이 지표에서만 뺍니다.
- **참고인 이유:** `grasp_dist = (파지 프레임의 손목 추종 오차) + (손목–손가락 끝 편향, 모든 알고리즘에 같음)`이라 알고리즘 사이 차이는 한 프레임의 추종 오차뿐입니다. TCP가 플랜지라 절대값도 수 cm 아래로 나올 수 없습니다.

#### 2.12 최소 조작성 (`min_manipulability`)

- **계산:** 프레임마다 TCP 야코비안(6×7)으로 `w = sqrt(det(J·Jᵀ))`를 구하고, 에피소드에서 가장 작은 값
- **왜:** 0에 가까우면 특이 자세(팔을 쭉 편 자세 등)입니다. 특이 자세 근처에서 DLS는 안정적으로 지나고 닫힌 해는 불안정해지는 차이를 설명합니다.

## 4. 집계 (`summary.md`)

- 에피소드 하나가 케이스 태그를 여러 개 가질 수 있으므로 **태그마다 한 번씩** 세어 집계합니다.
- 지표마다 표 하나. 행 = 케이스, 열 = 알고리즘, 칸 = **"중앙값 (최악값)"** (최악값 = 최댓값, 최소 조작성만 최솟값). 칸마다 에피소드 수를 적고 **5개 미만인 칸은 표시**합니다 (멘토 Q5 답 없음, 초안 유지).
- 축 순서로 둡니다: 정확도 → 속도 → 궤적 품질 → 안전 확인(0이 아닌 칸만) → 참고
- 속도 축은 케이스별 차이가 작으면 알고리즘별 한 줄로 줄여 적습니다.
- **논문 결론용 요약:** 알고리즘마다 정확도(2.1, 참고 2.2), 속도(2.3), 궤적 품질(2.4~2.7)을 한 줄로 모읍니다.
